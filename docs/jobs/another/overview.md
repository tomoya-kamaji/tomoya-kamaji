## バリューを発揮した点

### Rails から Node.js（TypeScript）への DDD の思想を取り入れたリプレイス

**■ 背景**
当初、サーバサイド言語として Rails を使用していたが下記 2 点の理由から保守に工数がかかっていた。

- 業務委託人材が入れ替わりで対応していたため、コードに統一感がなく複雑になっている
- Rails は型がなく動作させるまで処理が追いづらく保守に工数がかかる

上記理由から、Node.js（TypeScript）へのリプレイスを CTO 主導のもと 2 人で進めた。

**■ 発揮したバリュー**
初めての言語（TypeScript）、初めての設計手法（DDD）であり苦労したが、TypeScript は公式ドキュメント、DDD は『ドメイン駆動設計（モデリング / 実装ガイド）』等の書籍で概念を短期間でキャッチアップして貢献した。

■ 設計について意識した点

必ず依存の向きが逆転しないように意識して、下記を指針に実装を行った。

「Presenter 層は Usecase 層のみ依存できる、Usecase 層は Infra 層の interface に依存できる。Infra 層の実態には依存できない」

依存のルールを明確にすることで、各層での役割が明確になり迷いなく実装できるようになった。

■ 更新系と取得系の処理について

ドメイン層を用いて実装を行っていく中で、複数集約を跨いで値を取得することもあったため取得系の処理が肥大化してしまうことがあった。

そこで、更新・作成系の処理はドメインモデルを経由して DB（Infra 層）にアクセスし、取得系の処理は別途取得用のモデル（CQRS）を定義して DB にアクセスするように実装した。

更新や作成はドメインルールを逸脱するとデータ不整合が起こる可能性があるが、取得の際にはデータ不整合は起こらない。また、一覧系の API などは取得するテーブルが肥大化し、ドメインモデルを経由するのが困難なためこの判断をした。

取得系と更新系でモデルを分けることで、それぞれに適したクエリの発行ができるようになった。
→ [詳細](ddd.md)

### ユーザ検索機能：リプレイス、全文検索エンジンの実装、パフォーマンス・チューニング

**■ 背景**
企業側のメイン機能であるユーザ検索機能のリプレイスに伴い、全文検索エンジンの実装とパフォーマンス・チューニングを行った。

- 全文検索の課題：RDB の LIKE 句による前方後方一致での検索ノイズが多く、改修が必要だった
- パフォーマンスの課題：検索条件の複雑化に伴いテーブルの JOIN が肥大化し、コードも複雑になり改修しづらくなっていた

**■ 発揮したバリュー**
上記課題を解決するため、検索部分に Elasticsearch を使用する方針を決定し、setting・mapping の作成から検索機能の実装まで一通り行った。

■ 具体的な実装

- Elasticsearch の analyzer、index の定義（analyzer は Ngram と Kuromoji を使用）
- MySQL から Elasticsearch のドキュメントへのデータの流し込み（バッチ処理の実装）
- 検索 API 実装：検索クエリの作成

■ 意識した点、苦労した点

「検索ノイズが少なく、検索漏れも少ない全文検索エンジン」の構築に苦労したが、最終的に Ngram と Kuromoji を併用する方法で実装を行った。

- Ngram はノイズが多いが検索漏れが少ないため、必須の検索条件（query の must 句）に定義する
- Kuromoji は検索漏れは多いがノイズが少ないため、任意の検索条件（query の should 句）に定義する

両者を検索条件に含めることで、検索ワードの類似度が高い（`_score` が高い）ものが上位に表示されるようになった。

■ 結果

2.0 秒かかっていた検索処理を 0.5 秒まで改善することができた。また、検索時の実装がシンプルになりコードの可読性も高くなった。

### 障害対応、Sentry 対応

**■ 背景**
サーバサイド専任がほぼ 1 人のため、サーバサイドに関与する障害や Sentry 通知はほぼすべて対応した。

**■ 意識した点、発揮したバリュー**
■ 通知が来たらまず 1 次対応すること

バグをすぐに検知する仕組みとして Sentry を Slack に通知しており、通知が増えると放置しがちなため、通知が来たそのときに 1 次対応することを徹底した。

1 次対応してすぐに対応する必要があれば hotfix で対応し、1 時間ほどで修正できそうであればその場で修正、それ以外は技術的課題としてタスク化した。

■ ログを吐いて、デバッグがしやすいように

Sentry 通知が来た際などにサーバログから原因調査しやすいよう、特に定期バッチなど処理が追いづらいものは多めにログを出力するようにした。

### OpenAPI（Stoplight）の導入

**■ 背景**
元々フロントとの API 連携を Notion や Jira などのドキュメントツールで行っており、フォーマットがバラバラなことに起因してコミュニケーションコストが発生していた。
また、開発チームが大きくなったことを見据えて API 仕様を標準化して残したいと考えた。

**■ 発揮したバリュー**
API ドキュメント化の手法を調査し、[Stoplight Studio](https://stoplight.io/studio/) を使用した OpenAPI 作成を提案して導入から運用まで行った。
半年間ほど運用する中でフロントメンバーにも好評で、コミュニケーションコストの削減につながった。
