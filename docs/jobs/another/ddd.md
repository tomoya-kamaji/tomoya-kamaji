### 課題

既存の Rails コードベースは、業務委託メンバーの入れ替わりで書き方に統一感がなく、型もないため実際に動かすまで処理を追いにくい状態だった。

### 判断

人が替わっても品質を保てることを軸に、TypeScript と DDD を採用した。

- TypeScript：型で入出力の契約を明示し、コードを読むだけで処理を追えるようにする
- DDD：業務ルールをドメインモデルに集約し、書き手による実装のばらつきを抑える

あわせて、作成・更新系はドメインモデル経由、参照系は専用モデルを直接返す CQS（コマンドクエリ分離）を取り入れた。
更新時はドメインルールによる整合性保護が必須だが、参照時はデータ不整合が起きない。
一覧 API は JOIN するテーブルが多く、無理にドメインモデルを通すと肥大化するため、参照と更新で経路を分けた。

### 成果

- CTO と 2 名でドメインモデル図・アーキテクチャ・テーブル・API の設計から実装までを担った
- 新規開発を止めず、約 1 年かけて約 120 エンドポイントをすべて移行した
- TypeScript と DDD は実務未経験だったが、公式ドキュメントと書籍でキャッチアップして設計を主導した
