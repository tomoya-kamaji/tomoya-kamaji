### 軽量な設計プロセスの導入と定着

**課題**
設計フェーズがなく、要件・仕様の認識差が実装段階で表に出ていた。1 PR の変更規模も大きく、レビュー負荷とリリース後の改修再発が課題だった。

**判断**
重い設計工程を入れても定着しないと考え、「最小限の設計ドキュメント + レビュー観点の固定 + PR の粒度基準」の 3 点に絞った。

- 設計ドキュメントは API 仕様とデータモデルだけに絞った
- 設計レビューを定例化し、「影響範囲」「代替案」をテンプレートの観点にした
- PR は小さく早くマージする基準を決め、未レビューのものはマージしないルールにした
- 設計・決定事項・振り返りを Notion に集約し、後から探せるようにした
- 月次の振り返りで運用を見直し、チームに定着させた

**成果**
事前合意で不整合を早期に吸収し、要件起因の手戻りとリリース後の改修再発が減った。PR あたりの変更ファイル数も縮小し、設計からリリースまでのサイクルが安定した。

### チーム運用の強化

- レビュー文化とルールを明確にし、品質の底を上げた
- 監視・アラート（ログ・トレーシング）の観点を設計段階で織り込み、運用時の検知性を上げた

## マネジメント経験

### マネジメントの対象と責務

- 対象：エンジニア 3 名を含む開発チーム（計 5 名）の設計・開発プロセス・コード品質・1on1
- 責務：手戻りや PR 肥大化によるレビュー滞留をなくし、品質を保ちながら自律的かつ安定した速度で継続リリースできる状態にすること

### マネジメントの方針

書籍『リーダーの仮面』などの考え方をベースに、「一定のシンプルな方針・ルールを作り、それ以外はメンバーの裁量に任せる」方針をとった。
細かい管理や重いプロセスは形骸化しやすいため、守るべき最小限のルールだけを定義し、各自が自律的に判断・実装できる環境を整えた。

### 工夫したルールと運用

- 実装前のすり合わせ：実装前に作る資料を API 仕様とデータモデルの 2 つに絞り、影響範囲と代替案をレビュー観点にした
- コーディング・PR の基準：共通のコーディングルールに沿って実装し、PR は小さく分けて未レビューのままマージしない
- ボトルネックの最優先解消：レビュー待ちや仕様確認で自分がボトルネックになっているときは、自身の実装を止めてでもレビューや相談対応を最優先で行った
- 定期的な見直し：月 1 回の振り返りや 1on1 を通じてルールを見直し続けた。ルールが磨かれ、チームの自走力が高まっていく過程に大きなやりがいを感じた

## この経験から得たもの

- 軽量でも実効性のある設計プロセスの設計と運用
- 変更粒度の最適化による、品質とスループットの両立
