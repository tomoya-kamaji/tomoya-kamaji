## プロダクト概要

「決裁者にアプローチしたい営業・事業責任者様」と「課題解決の提案を受けたい決裁者様」を繋げる B2B リードジェネレーションプラットフォーム「SHOWDONE」を開発

<https://showdone.jp>

## 体制・稼働

- 営業：代表 1 名
- プロダクト：自分（フルタイム 1 名）+ 業務委託
- 2026 年 2 月からフルタイムの業務委託として参画（2026 年 1 月までは検索連動型広告、医療系 SaaS と並行稼働）

## 主な担当業務

■ プロダクトマネジメント・事業推進

- NSM（北極星指標）およびサブ指標の策定、SQL・PostHog によるダッシュボード構築
- プロダクトバックログの管理、優先順位付け、仕様策定
- 仮説検証とデータに基づく機能の継続・撤退判断

■ フロントエンド・バックエンド・インフラ開発（Next.js × NestJS）

- フロントエンド（Next.js）・バックエンド（NestJS）のアーキテクチャ設計・標準化
- テーブル設計（Prisma / PlanetScale）、API 設計、実装
- Zod × OpenAPI によるスキーマ駆動開発の導入・運用
- モノレポ化、表示速度のパフォーマンス・チューニング、AWS コスト最適化
- 要件整理から TDD 実装・並列レビュー・PR 作成までの AI 開発ワークフロー（Skill）構築

■ AI 機能の設計・実装・品質管理

- 外部フレームワークに依存しない自前 AI エージェント基盤の設計・実装
- URL からのサービス自動登録、オファー文面添削・下書き生成、対話型商材探索の実装
- Langfuse を用いたトレース・トークン・コストの可視化と評価 CLI の構築

■ 開発以外の業務

- 業務委託エンジニア向けのタスク切り出し（1 PR 単位の縦割り定義）と完了条件の策定
- 顧客インタビューの実施と週次でのプロダクト還元
- 交流会・カンファレンスでの営業

## バリューを発揮した点

### NSM（北極星指標）と 8 つのサブ指標の策定による判断基準の構築とファネル改善

**■ 背景**
参画当初、施策や実装の優先順位を決めるチーム共通の基準がなく、どの施策に注力すべきか判断しづらい状態だった。

また、プロダクト専任が自分 1 名という限られたリソースの中で、売上・事業成長に直結する施策へ集中する必要があった。

**■ 発揮したバリュー**
施策や実装に入る前に、プロダクトの存在意義・ペルソナ・価値交換の仕組みを言語化し、CEO と合意して判断の土台を作った。

■ 指標設計とボトルネックの特定

NSM（目標指標）を「月間有効商談数」に定め、その配下に 8 つのサブ指標を置いて SQL と PostHog で定義・ダッシュボード化した。

■ 各ファネルの改善と撤退判断（半年で主要機能 30 件超をリリース）

- 計測：PostHog による登録ファネル計測、決裁者側の商談完了報告・BANT 収集基盤を実装し、有効商談を計測可能にした
- 登録・獲得：最小情報で即やり取りできるゲストチャット、パブリックプロフィール、名刺本人確認を実装し、登録ハードルを下げた
- 送信・返信：送信履歴と候補者保存による重複送信防止、おすすめ候補のレコメンド、アクションリスト通知を実装し、「送る → 返す → 報告する」ループを改善した
- 検証と撤退判断：未登録の決裁者に紹介で届く「相互紹介機能」を企画・リリースしたが、利用が伸びず数字が動かなかった。複数人が関わる機能は片側のユーザー蓄積など「使われる状況の設計」が先決であると学び、本開発を見送る判断を行った

### フロントエンド（Next.js）・バックエンド（NestJS）のアーキテクチャ標準化と AI 駆動開発の仕組み化

**■ 背景**
旧構成と新構成のコードが混在しており、新規実装で従うべきアーキテクチャが定まっていなかった。

また、少人数（フルタイム 1 名 + 業務委託）で高速に機能開発を進めるため、迷いなく実装・レビューできる規約とタスク分割の仕組みが必要だった。

**■ 発揮したバリュー**
フロントエンドとバックエンドの標準構成を策定し、AI エージェントや業務委託メンバーも同じ手順で開発できるよう Skill とルールに落とし込んだ。

■ バックエンド（NestJS）の設計で意識した点

Domain・UseCase・Infra のレイヤーに分け、複雑なロジックは純粋関数で表現する方針を立てた。

最初からすべてを重厚なドメインモデルにはせず、複雑さに応じて純粋関数や判別共用体へ引き上げる基準を設け、過剰設計を防ぎつつドメイン知識を保護できるようにした。

■ フロントエンド（Next.js）の設計で意識した点

サーバー状態（TanStack Query）・画面固有の状態（React Context）・UI の 3 層構成を新規実装の標準にした。

ローディングは Suspense、エラーは ErrorBoundary に委譲することで、各画面コンポーネント内の条件分岐を減らし見通しを良くした。

■ タスク分解と開発ワークフローの標準化

Notion の Task に完了条件を明記し、1 PR でリリースできる縦割りの単位に分割する運用を整えた。

さらに、要件整理 → タスク分割 → TDD 実装 → 並列レビュー → PR 作成までの一連の流れを Skill にまとめ、人間の判断が必要なタスクと AI・業務委託に任せられるタスクを切り分けて高速に開発を回せるようにした。

### 独自 AI エージェント基盤の構築と Langfuse による観測・評価運用

**■ 背景**
サービス登録やオファー文面の作成、商材探索など、ユーザーの入力・運用コストが高い工程がボトルネックになっていた。

一方で、LLM を組み込む際には検索前の推測による誤提案や過剰な質問、トークンコストの増加を防ぐ必要があった。

**■ 発揮したバリュー**
ユーザーの手間を削減する複数の AI 機能を設計・実装し、本番で使える品質とコスト管理の基盤を整えた。

■ 具体的な実装

- URL を入力するだけでサービスページを自動生成する機能
- 相手に合わせてオファー文面を添削・下書き生成する機能
- 対話形式で課題を整理し商材を探索するエージェント機能

■ 意識した点、工夫した点

ブラックボックス化しやすい外部のエージェント用フレームワークはあえて使わず、指示文・ツール・権限制御を自前で実装した。

特に段階的な対話が必要な商材探索では、フェーズごとに呼び出せるツールを厳密に制限することで、検索前の早まった提案やユーザーへの過剰な質問を防いだ。

■ 結果

Langfuse を導入してトレース・トークン消費量・コストを常時可視化し、評価用 CLI でモデルやプロンプト構成を比較できるようにした。

---

### パフォーマンス・チューニングとモノレポ・インフラ基盤の改善

**■ 背景**
機能拡張に伴い、画面の表示速度低下や AWS・LLM 呼び出しのコスト増加が課題になっていた。

また、リポジトリが分かれていたことでフロントエンドとバックエンドを跨ぐ変更に手間がかかっていた。

**■ 発揮したバリュー**
新機能開発と並行して、開発体験と本番環境のパフォーマンス・コスト改善を一貫して行った。

■ 具体的な取り組みと結果

- 散在していたリポジトリをモノレポに統合し、Zod / OpenAPI による型連携と横断的な変更をスムーズにした
- 認証処理、DB クエリの並列化を見直し、画面の表示速度を改善した
- AWS 構成の整理と LLM 呼び出しの最適化を行い、インフラおよび API の運用コストを削減した

## 使用技術

フロントエンド：TypeScript、React、Next.js、TailwindCSS、Jotai、Radix UI

バックエンド：TypeScript、NestJS、Prisma

インフラ：AWS（ECS、S3、CloudFront、Route 53、Lambda、API Gateway 等）、AWS CDK、Vercel

データベース：MySQL（PlanetScale）

AI・計測：Langfuse、PostHog
