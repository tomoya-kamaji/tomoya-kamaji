## 概要

前任オーナーの退職に伴い、秒間 6,000 リクエストを処理する広告配信サーバのモジュールオーナーを引き継いだ。
収益の柱でありながらテストと監視が手薄だったため、テスト・監視・性能の 3 軸で立て直した。

## 重要ロジックのテストと CI

**課題**
テストがほとんど無く、レビューのたびにコードから振る舞いを読み解く必要があった。

**判断**
API レベルの統合テストは保守コストに対して恩恵が小さいと判断し、広告配信のコアロジックに絞って単体テストと CI を整えた。

**成果**
レビュー負荷が下がり、テスト自体がロジックの仕様書として後任のキャッチアップにも機能するようになった。

## 広告不足の検知

**課題**
特定のメディアで広告在庫が足りず配信されないケースがあったが、検知する仕組みが無かった。

**判断**
Google Cloud のマネージドサービス（Cloud Logging のログベース指標 + Cloud Monitoring）を組み合わせて Slack へ通知する仕組みを作った。

**成果**
取りこぼしていた配信枠を即座に検知し、ビジネスチーム経由でメディアへ対応を依頼できるようになった。結果として**月約 20 万 imp**を改善した。

## 予測モデルの読み込み失敗の検知

**課題**
起動時にクリック率の予測モデルを読み込む処理がまれに失敗していた。失敗時はモデルなしの配信にフォールバックするため、放置すると収益減に直結する。

**判断**
広告不足と同じ監視基盤に載せつつ、Goroutine で動いていた読み込み処理のエラーハンドリングとタイムアウトも見直した。

**成果**
収益が落ち続ける前に検知できるようになり、**収益減を未然に防いだ**。

## 性能改善

Redis とメモリキャッシュの 2 層構成にし、秒間 6,000 リクエストの配信負荷を下げた。
